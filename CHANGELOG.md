# Changelog

## 0.16.0 — 2026-10-29

### Added
- **Already-delegated accounts are held.** `check_payment` (and so `check_transaction`, `check_authorization` and
  `check_circle_request`) takes an optional `account_code`, the paying account's `eth_getCode` result, and
  `expected_delegates`. If the code is an EIP-7702 delegation designator (`0xef0100` + address) to a contract not
  in `expected_delegates`, every payment is held as `ACCOUNT_DELEGATED`, naming the delegate: an authorization
  signed outside the guarded client leaves exactly this trace. Plain accounts and ordinary contract wallets pass;
  unreadable code is held (`INVALID_ACCOUNT_CODE`). The SDK still never calls an RPC; you pass the code in.
  New `check_account_code()` and `delegate_from_code()`. Suggested by Carlos (Bloqarl) on DEV.to.

## 0.15.0 — 2026-10-28

### Added
- **Address-poisoning check.** With `known_recipients` set, a recipient that is not known but imitates a known
  payee (at least 7 matching hex characters, at least 3 at each end, such as `0x2ffb…b7ee` for
  `0x2ffb88…472deb7ee`) is a REJECT, `LOOKALIKE_RECIPIENT`, naming the payee it imitates and the matching ends.
  Attackers plant such addresses in a wallet's history with tiny transfers and wait for the next payment to be
  copied from there. A random address matches this way about once in 140 million tries per known payee. Runs
  after the sanctions and blocklist checks, in every check that pays (`check_payment`, `check_transaction`,
  `check_authorization`, `check_circle_request`, the MCP server). `sra_riskgate.counterparty.find_lookalike()`.

### Changed
- Sanctions list re-checked against the upstream OFAC extract on 2026-10-28: unchanged since 2026-10-01
  (124 EVM addresses), so the bundled list is current.

## 0.14.0 — 2026-10-27

### Added
- **Circle Wallets (developer-controlled).** `check_circle_request(operation, body, ...)` checks a request before
  it is sent to Circle's API, which signs as soon as it accepts it: transfers (USDC by token address or a
  configured Circle token id, and native USDC on Arc) go through `check_payment`; contract executions are rebuilt
  into calldata and go through `check_transaction` (so `approve` is held); `sign/typedData` goes through
  `check_authorization` (x402, Circle Gateway, Permit); `sign/transaction` through `check_transaction` (including
  EIP-7702). `sign/message` and wallet upgrades are held. Accepts plain dicts or the official SDK's request
  models.
- `guard_circle_wallets(api, ...)` wraps the SDK's `TransactionsApi` / `SigningApi` so money-moving and signing
  calls are sent only on approve, raising `CircleRequestBlocked` otherwise; read-only calls pass through.
- `pip install "sra-riskgate[circle]"` installs `circle-developer-controlled-wallets`.

## 0.13.1 — 2026-10-26

### Fixed
- **Payments from Circle's own Gateway SDK were held.** `@circle-fin/x402-batching` 4.x signs Gateway
  authorizations to stay valid for seven days plus 100 seconds, just over 0.13.0's seven-day default, so every
  one was held as `LONG_LIVED_AUTHORIZATION`. The default `max_gateway_validity_seconds` is now eight days. A real
  payment generated by the SDK is now part of the tests.
- Long validity periods are reported in days.

## 0.13.0 — 2026-10-26

### Added
- **Circle Gateway batched x402 payments.** `check_authorization` recognises a `TransferWithAuthorization`
  signed for Gateway's `GatewayWalletBatched` domain (version `"1"`) with Circle's GatewayWallet contract as
  `verifyingContract`, on Ethereum, Base, Base Sepolia, Arc and Arc Testnet. Gateway requires these to stay valid
  for at least three days, so they have their own limit, `max_gateway_validity_seconds` (default seven days),
  instead of being held by the one-hour limit; the decoded payment gets every other check. A Gateway-named
  domain with any other contract, version `"2"` (EURC, cirBTC), or another primary type is held, and a Gateway
  authorization valid for less than three days is held as `GATEWAY_VALIDITY_TOO_SHORT`.
- `sra_riskgate.chains.GATEWAY_WALLET_ADDRESSES` and `is_gateway_wallet()`.

## 0.12.1 — 2026-10-25

### Fixed
- **EIP-7702 delegations were not seen.** A type 4 transaction whose `to` and calldata were a clean USDC
  `transfer` was approved even when its `authorizationList` delegated the wallet's account to a contract,
  on every chain with chain id 0. `check_transaction` now holds any type 4 transaction, and any transaction
  with a non-empty `authorizationList`, as `CODE_DELEGATION`, before every other check; the explanation names
  the contract and whether the authorization is valid on every chain. Reported by Carlos (Bloqarl) on DEV.to.

### Added
- `check_delegation(authorization)`: for a standalone EIP-7702 authorization (viem `signAuthorization`,
  eth-account `sign_authorization`), which neither a transaction check nor `check_authorization` sees. It
  always holds (`CODE_DELEGATION`); route your wallet library's authorization signing through it.

## 0.12.0 — 2026-10-25

### Added
- **Arc** (Circle's blockchain), mainnet `5042` and testnet `5042002`, in every check: `check_payment`,
  `check_transaction`, `check_authorization` and the x402 hooks (`eip155:5042`, or the names `arc` and
  `arc-testnet`). USDC's ERC-20 interface is at `0x3600000000000000000000000000000000000000` (6 decimals).
- On Arc, USDC is the native asset, so `check_transaction` treats a plain native send (value, no calldata) as a
  USDC payment: the value is read with 18 decimals, rounded up to a whole micro-USDC so dust cannot pass a
  limit, and gets every payment check. Native value sent together with a contract call is held
  (`NATIVE_VALUE_TRANSFER`), as is native USDC sent to the USDC contract itself.
- `chains.NATIVE_USDC_CHAINS` and `chains.NATIVE_USDC_DECIMALS`.

No change to any decision on Ethereum, Base or Base Sepolia: native value there is still ETH and still held.

## 0.11.0 — 2026-10-25

### Added
- `check_authorization(typed_data, *, sender=None, chain_id=None, now=None, max_validity_seconds=3600, **policy)`:
  checks the EIP-712 typed data an agent signs for an x402 payment (EIP-3009 `TransferWithAuthorization`
  or `ReceiveWithAuthorization`) before it signs. Checks the domain is USDC on a supported chain, the
  type definition is USDC's, `from` and `chainId` match, and the authorization is current and short-lived
  (`AUTHORIZATION_EXPIRED`, `AUTHORIZATION_NOT_YET_VALID`, `LONG_LIVED_AUTHORIZATION`), then runs the decoded
  payment through `check_payment`. An EIP-2612 `Permit` is held as `TOKEN_APPROVAL`; other types as
  `UNSUPPORTED_SIGNATURE`. Never raises; anything unexpected is held.

No change to `check_payment`, `check_transaction`, `check_dispute_verdict` or any existing decision.

## 0.10.0 — 2026-10-24

### Added
- `check_dispute_verdict(dispute, verdict)`: checks a dispute verdict against the dispute window computed
  from the dispute's own dates. A false `outside_dispute_window` claim is replaced by
  `dispute_window_claim_contradicted`, and a `deny` or `dismiss` resting on it becomes
  `escalate_to_human` with no refund. Never produces a refund; never raises; returns a copy.
- `dispute_window(paid_at, filed_at, window_days)` and `DisputeWindow`.
- `eval/dispute_window_check.py` measures the check on the published predictions: wrongful denials
  26.0% -> 0.85%, wrongful refunds unchanged at 2.2%, outcome accuracy 77.8% -> 78.7%.
- `eval/profile_bench.py` profiles the dispute errors and checks train/test overlap (0 exact duplicates;
  99.3% payment accuracy on test cases with no template twin in training).

No change to `check_payment`, `check_transaction` or any existing decision.

## 0.9.0 — 2026-10-24

### Added
- `check_transaction(tx, *, chain_id=None, sender=None, **policy)`: checks the exact transaction an
  agent is about to sign (`to`, `data`/`input`, `value`, `from`, `chainId`, as for web3.py). A plain
  USDC `transfer` is decoded and checked by `check_payment` with the same policy arguments. Everything
  else is held: token approvals (`TOKEN_APPROVAL`, plus `UNLIMITED_APPROVAL`), other functions
  (`UNSUPPORTED_FUNCTION`), other contracts (`UNSUPPORTED_ASSET`), native ETH (`NATIVE_VALUE_TRANSFER`),
  unsupported chains, mismatched `from`/`chainId` (`TRANSACTION_MISMATCH`) and malformed calldata
  (`INVALID_TRANSACTION`). It never raises; an unknown policy argument is `CONFIGURATION_ERROR`.
- `decode_erc20_transfer(calldata)`: strict decoder for ERC-20 `transfer` calldata.

No change to `check_payment` or any existing decision.

### Development
- `eval/run_eval.py` sends its own `User-Agent`, so benchmark runs against a vLLM Pod on Runpod are not
  refused with HTTP 403 (the same fix as sra-riskgate-mcp 0.5.1).

## 0.8.0 — 2026-10-21

Counterparty policy: checks on who is on the other side of a payment. All new checks are off by
default, so existing callers see no change in decisions.

### Added
- `known_recipients` (on `check_payment` and `RulePreFilter`): when given, a payment to an address
  not on the list is held with `NEW_COUNTERPARTY`, the standard control against vendor-impersonation
  and payment-redirection fraud. `None` (default) turns it off; an empty list holds every payment.
  Nothing in the payment request or memo can add an address to the list.
- `blocked_addresses` (on `check_payment` and `RulePreFilter`): a payment from or to a listed address
  is rejected with `BLOCKLISTED_ADDRESS` plus `BLOCKLISTED_SENDER` / `BLOCKLISTED_RECIPIENT`. Runs right
  after the OFAC match, so it wins over every hold.
- `SANCTIONS_LIST_STALE`: informational flag when the sanctions list's `as_of` date is more than
  `sanctions_max_age_days` (default 90) days old. It never changes the decision. Lists without a
  date are not flagged; `sanctions_max_age_days=None` turns it off.
- `RulePreFilter.screen_blocklist()` and `RulePreFilter.sanctions_list_age_days()`.
- `RulePreFilter.inspect()` accepts per-call `known_recipients` and `blocked_addresses`, added to the
  gate's own lists.

### Fail-closed behaviour
- A malformed address list (a bare string, a non-address entry, a mapping) is a configuration error:
  `check_payment` returns `reject` with `CONFIGURATION_ERROR`, and `RulePreFilter` raises `ValueError`.
  A typo in a policy list can never silently weaken it.

### Docs
- README: counterparty policy section, staleness note, LangChain integrations listing
  (langchain-ai/docs#6918), links to the official and community (mradermacher static and imatrix)
  GGUF builds.

### Tests
- 41 new tests. The suite now pins "today" in `conftest.py` so results do not change with the calendar.

## 0.7.2
- New informational flag `ROUND_AMOUNT`: a whole-number amount at or above 10,000 USDC is flagged.
  Large round-number transfers are a common transaction-monitoring signal; the 10,000 default mirrors
  the US currency transaction report threshold for cash (CTRs themselves do not apply to stablecoin
  transfers).
- **It never changes the decision.** An approve stays approve and a hold stays hold; the explanation says
  the flag is informational and that many such payments (payroll, settlements) are legitimate.
- Configure with `RulePreFilter(round_amount_threshold=...)`, or pass `None` to turn it off.
- Because `check_payment`'s default ceiling is 1,000 USDC, the flag appears there only alongside
  `HIGH_VALUE_TRANSFER` unless you raise `max_amount`. `RulePreFilter`'s default ceiling is 50,000, so
  round amounts from 10,000 to 50,000 now approve with the flag instead of with no flags.
- README: the decision table now lists the dust rule (below 0.000001 USDC) and the round-amount flag.
- Suggested by an external review.

## 0.7.1
- Fix: a USDC amount below one atomic unit (0.000001 USDC) is now rejected with `INVALID_PAYMENT`
  ("below the smallest USDC unit"). Such an amount rounds to zero on-chain and can never execute, but
  0.7.0 and earlier approved it (for example `amount=1e-7`). The check lives in `TransactionPayload`
  validation, so `check_payment`, `RulePreFilter`, the AgentKit provider and the MCP rule tools all
  reject it; the AgentKit provider now blocks it before sending instead of failing at encoding.
- Amounts of at least 0.000001 USDC decide exactly as before; a remainder below one unit (e.g.
  1.0000001) is still rounded down on-chain as before. Non-USDC tokens are unaffected.
- Reported by an external review of 0.6.1.

## 0.7.0
- **New: offline OFAC SDN address match.** `check_payment` and `RulePreFilter` now **reject** a payment
  whose sender or recipient is on the US Treasury OFAC SDN list, with flags `OFAC_SDN_MATCH` and
  `SANCTIONED_RECIPIENT` / `SANCTIONED_SENDER` and required actions `reject_payment`,
  `refer_to_compliance`. The package bundles 124 Ethereum-format addresses (as of 2026-10-01), taken
  from the open-source ofac-sanctioned-digital-currency-addresses extraction of OFAC's list. No network
  call or API key.
- In `check_payment` the sanctions match runs first, so a sanctioned counterparty is a reject even on an
  unsupported chain or token.
- New `SanctionsList` (`from_file`, `from_addresses`, `bundled`) and `is_sanctioned()`. Pass
  `sanctions_list=` to use a fresher list, or `check_sanctions=False` to turn the match off (results then
  carry `SANCTIONS_NOT_CHECKED`).
- The x402 hooks and the AgentKit action provider get the same check through `RulePreFilter`.
- Fails closed: if the list cannot be loaded, `check_payment` returns `hold` (`CHECK_FAILED`).
- **Behaviour change:** payments to or from listed addresses that were approved before are now rejected.
  Everything else decides exactly as in 0.6.1.
- It is an exact match against a dated snapshot, not a sanctions screening service or a compliance
  determination; the README says so.

## 0.6.0
- New `check_payment()`: one fail-closed call before every payment. It checks the asset and chain
  (USDC on Ethereum, Base, Base Sepolia), validates addresses and amount, runs `RulePreFilter` and scans
  the untrusted request text for self-asserted verification claims. Invalid payments and bad
  configuration are rejected; unsupported chains or tokens and any internal error become `hold`. It
  never raises on bad payment data, so callers cannot accidentally fail open. Default per-payment
  ceiling is 1,000 USDC.
- README: quick start for `check_payment` and a link to the
  [agent-payment-guard](https://github.com/sriram1983007-dev/agent-payment-guard) Agent Skill.
- No change to existing APIs or decisions.
- README wording (GitHub copy): model results are described as measured by the author in two runs, not
  "independently reproduced". The PyPI page for 0.6.0 still shows the old wording until the next release.

## 0.5.1
- `scan_payload_claims` hardened after a code audit:
  - text is normalised before matching (Unicode compatibility forms, zero-width characters, Cyrillic and
    Greek look-alike letters), so "ｒｉｓｋ level: low" or "pre-vеrified" no longer slip through;
  - "System:" / "Assistant:" only match at the start of a line, so ordinary text such as
    "Billing system: invoice 42" is no longer held;
  - payloads too large (over 10,000 text fields) or too deeply nested to scan now return a
    `payload_too_large_to_scan` claim (hold) instead of being partly skipped.
- `RulePreFilter`: when no peg deviation is supplied, the assessment now carries the flag `PEG_NOT_CHECKED`
  and says the depeg check was skipped, instead of looking like a perfect peg. Decisions are unchanged.
  `TransactionPayload` gains a read-only-in-spirit `peg_observed` field, set automatically.

## 0.5.0
- New `scan_payload_claims()`: detects self-asserted verification claims in untrusted payment text
  (for example "risk level: low (verified offline)", "sanctions screening passed", "pre-approved",
  "ignore previous instructions"). Use it to hold a payment, never to reject it.
  On sra-stablecoin-risk-bench it flags all 4 of SRA-RiskGate-4B's unsafe approvals on the held-out
  test set with 0 false holds on 3,358 legitimate payments (test + train). The rules were written after
  those failures were identified, so this fixes a known weakness and is not an independent evaluation.
- x402 hooks: payment requirements whose `extra` contains such claims are aborted with
  `sra_riskgate_payload_claims` (disable with `check_payload_claims=False`).
- AgentKit action provider: a transfer whose memo contains such claims is held, not sent.
