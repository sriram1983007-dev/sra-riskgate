\begin{abstract}
AI agents now pay for APIs, data and compute in stablecoins, through x402, EIP-3009 authorizations and smart accounts. These payments are final: a wrong decision before signing cannot be undone by a chargeback, and the request that tells the agent what to pay is written by the party being paid. We present SRA-RiskGate, an open-source system built on one design rule: \emph{the model judges, deterministic code enforces}. First, \emph{sra-riskgate} is a fail-closed Python library that checks the exact bytes an agent is about to sign on every signing path we know of (ERC-20 transfers, x402 signatures, Circle Gateway batches, ERC-4337 UserOperations, Circle Wallets requests, EIP-7702 delegations and standing allowances), confirms after settlement that exactly the approved payment arrived, and signs a chained, verifiable receipt for every decision. Second, we release a synthetic benchmark of 20,000 cases with real signatures, and SRA-RiskGate-4B, a QLoRA fine-tune of Qwen3-4B that raises payment decision accuracy on the held-out test split from 59.8\% to 99.6\% and lowers unsafe approvals from 34.6\% to 0.35\%. Third, an error analysis shows that the model's remaining failures cluster in two operations better done in code, trusting what untrusted text says about itself and comparing dates; moving the date comparison into code lowers wrongful dispute denials from 26.0\% to 0.0\%. Fourth, on 90 days of USDC and USDT payments on Ethereum mainnet, the library rejected 171 of 179 confirmed address-poisoning attacks before payment, covering \$3,326,190 of \$3,327,006 lost, and wrongly rejected 0 of 4,967 normal payments; the model alone stopped 2 of 58. All code, data and predictions are public, and the library's claims can be re-checked offline with one command.
\end{abstract}

\section{Introduction}

Payment protocols designed for software agents let an agent pay for an API call or a dataset by signing a stablecoin authorization in the middle of an HTTP exchange~\cite{x402,eip3009}. Three properties make this setting unusual. First, settlement is final: once a USDC transfer confirms, no intermediary can claw it back, so the only protection is a decision made \emph{before} signing. Second, the payment request is attacker-controlled text that reaches the agent's model, which makes indirect prompt injection~\cite{greshake,agentdojo,injecagent} a direct path to moving money. Third, the agent may not sign a ``payment'' at all: it may sign an approval, a permit, a delegation of its whole account, or a batch in which a payment hides next to an approval. In October 2026 the Cloud Security Alliance reviewed flaws in x402 SDKs and recommended controls enforced outside the model, cumulative budgets, and the payer's policy, not the payee's request, deciding what is paid~\cite{csax402}.

This paper reports what we built, measured and learned while engineering such a control. Our contributions are:
\begin{enumerate}
  \item \textbf{A fail-closed pre-sign library} that decodes the exact bytes of every signing path an agent uses, applies one policy to all of them, and never turns an error into an approval (Section~\ref{sec:library}).
  \item \textbf{Verifiable decisions}: signed receipts chained so that an edited, deleted, inserted or reordered decision is detectable; an audit report built only from receipts that verify; a mapping of every decision flag to the OWASP LLM and agentic risk lists; and evidence packs that let a reviewer re-check every claim offline (Section~\ref{sec:verifiable}).
  \item \textbf{A benchmark and a 4B model} that runs on a laptop, in two versions, with every prediction published (Sections~\ref{sec:bench}--\ref{sec:results}).
  \item \textbf{An error analysis} showing which of the model's remaining failures belong in code, with a deterministic check for each and its measured effect (Section~\ref{sec:failures}).
  \item \textbf{A real-world evaluation} on confirmed address-poisoning attacks and real payments on two mainnets, separating what the library catches from what the model catches (Section~\ref{sec:real}).
  \item \textbf{An offline utility--security benchmark} for any payment guard, with baselines, so that blocking everything does not look like safety (Section~\ref{sec:guardbench}).
\end{enumerate}
The lesson that runs through all of them is simple. The model reads messy, partly adversarial evidence well. Arithmetic, signature decoding, list membership, address comparison and claim detection belong in code that cannot be talked out of its answer, and the system's safety must not depend on the model agreeing.

\section{Background and threat model}\label{sec:background}

\paragraph{Agent payments.} x402~\cite{x402} revives the HTTP 402 status code: a server answers a request with payment requirements (network, asset, amount, recipient), and the client retries with a signed EIP-3009 \code{transferWithAuthorization}~\cite{eip3009} that a facilitator submits on chain. Agents also send ordinary ERC-20 transfers, act through ERC-4337 smart accounts~\cite{eip4337}, or call custodial wallet APIs that sign on their behalf. All are push payments: the payer's key authorises the movement of funds, and confirmation makes it final.

\paragraph{Finality and remedies.} We follow~\cite{cacm}, which separates four terms that card payments blur. A \emph{reversal} undoes a held payment before release and needs a contract with that power (escrow, a two-of-three multisig). A \emph{refund} after finality is a new, voluntary transfer from the merchant. A \emph{chargeback}, a forced extraction by an intermediary, does not exist on these rails. A \emph{dispute} is the adjudication that resolves into one of the others; after finality an arbiter can force compensation only from collateral posted in advance, as a compensating transaction in the sense of the Saga pattern~\cite{sagas}.

\paragraph{Threat model.} The attacker controls the payment request and any text in it, can plant look-alike addresses in the paying wallet's history (address poisoning~\cite{poisoning}), and, when agents negotiate, controls the counterparty's messages. The attacker may also be the payee of a legitimate service that over-charges or asks for broader permissions than the payment needs. We assume the agent's key, the library's code and the payer's policy file are not compromised, and that the model may be manipulated. The goal is that no payment the payer's policy forbids is signed, that every decision can later be proved, and that legitimate payments are not blocked so often that operators turn the control off.

\section{The pre-sign library}\label{sec:library}

\paragraph{One decision, three outcomes.} Every check returns \code{approve}, \code{hold} or \code{reject} with reason codes (\emph{flags}), an explanation and required actions. The library defines 93 flags, each assigned a control category (injection, payee, negotiation, limits, permissions, integrity, compliance, market, fail-closed, settlement). The design is fail-closed throughout: no check raises on bad payment data; malformed input is rejected; anything unexpected, including a screening provider that times out, a corrupt spend ledger or a half-configured setting, becomes \code{hold}, never a silent pass.

\paragraph{Every signing path.} Table~\ref{tab:paths} lists the paths the library decodes. Each one reduces what is about to be signed to the payments it would make and the permissions it would grant, then runs the same payment checks: supported asset and chain, amount limits, depeg in both directions, an offline match against OFAC's sanctioned digital-currency addresses~\cite{ofac} (a dated snapshot, not a screening service), known-payee and blocklist policies, optional outside screening, rolling budgets and anomaly limits, and a scan of the untrusted request text. Anything that grants a permission rather than paying (an approval, a permit, a delegation) is held, because it lets someone move funds later without another check.

\paragraph{Who gets paid.} Address poisoning plants an address that shares the first and last characters of a payee the victim already uses. A recipient that is not a known payee but matches one in at least seven hexadecimal characters, at least three at each end, is rejected as \code{LOOKALIKE\_RECIPIENT}, naming the payee it imitates; a \emph{strict} mode also rejects matches of exactly three at each end. A request whose text asks to pay a new or different address (``our wallet address has changed''), or names an address that is neither payee nor sender, is held as \code{PAYEE\_CHANGE\_REQUEST}: the redirection behind invoice fraud, aimed at an agent instead of a clerk. A scan of a wallet's transfer history (\code{sra-riskgate scan}) lists look-alikes already planted there and writes a policy that blocks them.

\paragraph{Negotiations.} When agents negotiate before paying, each message can look fine on its own while the sequence redirects the money. A \code{PaymentSession} records the agreed payee, amount, token and chain, reads every counterparty message as received, and holds a payment that drifts from the terms, repeats one already paid, or follows an earlier request to pay elsewhere or to ignore the agent's rules. Such a request is remembered for the rest of the session, because a redirect is often made in one message and acted on several messages later. Only the principal can amend the terms, and each amendment is recorded with who made it and why.

\paragraph{One policy, many surfaces.} All settings live in one policy file whose SHA-256 is bound into every receipt. The same checks are exposed as a command line whose exit code distinguishes approve, hold and reject (so a script can stop on a hold), an MCP server~\cite{mcp,mcpserver} for desktop assistants and code editors, LangChain, CrewAI and Coinbase AgentKit integrations, x402 client and server hooks, a GitHub Action, and an ElizaOS plugin that wraps the agent's wallet so that only approved payments are broadcast. A server-side setting, such as which stablecoins are enabled, cannot be changed by the agent, so a manipulated agent cannot switch a check off.

\paragraph{Engineering practices.} Four practices mattered more than any single rule.
\emph{Test against what real software emits.} Our first validity limit for Circle Gateway (seven days) held every payment produced by Circle's own SDK, which signs for seven days plus 100 seconds; we found this only by testing against SDK output, and such a payment is now a test case. UserOperation decoding is tested against call data produced by viem and permissionless for seven account types.
\emph{Make the safe default the only default.} New tokens are off until enabled; registering a custom stablecoin cannot change a built-in one; a half-configured screening provider is a configuration error, not screening silently disabled.
\emph{Treat the flag vocabulary as an interface.} A test fails if a flag is added without a category and a risk mapping; the public API follows semantic versioning, and the latest major release changed no decision.
\emph{Assume reviews will find fail-open paths.} A review of the Elliptic screening adapter found that a sanctions listing nested inside a wallet's cluster entity was read as clean; the fix and a regression test followed. A known-answer self-check of 8 payments ships with the library and runs in every evidence pack.

\section{Verifiable decisions}\label{sec:verifiable}

A control that cannot prove what it decided is hard to audit and hard to fund. Every decision can carry a receipt signed with HMAC-SHA256 or an Ethereum key, over the canonical JSON of the decision, the payment, the policy hash, the library version and the time. Each receipt can also sign the SHA-256 of the previous one, so verifying a chain detects an edited, deleted, inserted or reordered decision; it cannot detect receipts cut off the end, so the latest link should be recorded elsewhere.

An \emph{audit report} is built from receipts alone. It verifies every receipt and the chain, then summarises the period, decisions and amounts per token, flags, policies, signers and risks addressed; receipts that do not verify are listed and excluded from every figure, and the report carries its own deterministic SHA-256 so that two parties can confirm they hold the same report. Each flag maps to entries in the OWASP Top 10 for LLM Applications 2025~\cite{owaspllm} and the OWASP Top 10 for Agentic Applications 2026~\cite{owaspagentic}; 13 of the 20 entries are addressed in part, and the 7 that are not (for example system prompt leakage and supply chain) are listed rather than hidden. The mapping is our own reading of the OWASP descriptions and has not been reviewed by OWASP.

An \emph{evidence pack} (\code{sra-riskgate evidence build}) gathers, offline, a known-answer self-check, the guard benchmark of Section~\ref{sec:guardbench} with every case, the OWASP coverage, an audit report, a hash of every source file and a manifest whose SHA-256 fingerprints the whole pack; \code{evidence verify} confirms that no file changed after it was built. The intent is that a grant assessor, an auditor or a customer can re-check the claims in this paper without trusting the author's machine.

\paragraph{Shared state.} Budgets enforced on one machine can be evaded by an agent running on several. An optional service (SRA-RiskGate Cloud, open source) adds a shared spend ledger, a threat feed of look-alike addresses that admits an address only when two organisations report it (or an operator approves it), and a vault of signed, chained receipts. The client checks locally first, so payment text never leaves the machine; only a locally approved payment is sent, the stricter decision wins, and an unreachable service gives \code{hold}.

\section{The SRA Stablecoin Risk Bench}\label{sec:bench}

\paragraph{Tasks.} Each case gives the model the current time, the policy, the payload (the payment or dispute exactly as received, marked untrusted) and the results of verification tools. \emph{Risk gate} cases cover three payment formats (x402 requirements, EIP-3009 authorizations, ERC-20 transfers) and ask for a JSON verdict with a decision, a risk level, flags and required actions. \emph{Dispute} cases cover three rails (direct payment, escrow, two-of-three multisig) and ask for an outcome, a mechanism, the settlement state and, for refunds, the exact amount, destination and idempotency key. There are ten dispute outcomes and eight mechanisms, and deliberately no ``chargeback''.

\paragraph{Generation and labels.} A deterministic generator perturbs clean cases: forged, expired, untrusted or out-of-scope risk attestations (small EIP-712~\cite{eip712} signed statements that travel with a request); sanctioned parties; expired or not-yet-valid authorizations; amounts over limits; wrong assets or networks; recipient and amount mismatches; and prompt-injection text in untrusted fields. All signatures are real secp256k1 EIP-3009 and EIP-712 signatures over simulated keys. Labels come from a rule engine whose decision order is documented with the dataset, and never propose a remedy the settlement state cannot support.

\paragraph{Splits and metrics.} There are 20,000 cases: 18,000 for training and 2,000 held out. The test split has 1,175 risk-gate cases (847 that should be held or rejected and 328 legitimate, including 69 with injected text) and 825 disputes. The open scorer~\cite{bench} reports decision accuracy, flag F1, the \emph{unsafe approval rate} (risky payments approved), over-blocking (legitimate payments blocked) and injection handling; for disputes, outcome accuracy, the \emph{impossible remedy rate}, the \emph{wrongful refund} and \emph{wrongful denial} rates and refund-detail accuracy. The composite SRA score averages a risk-gate and a dispute score.

\section{Model}\label{sec:model}

SRA-RiskGate-4B~\cite{model} is Qwen3-4B-Instruct-2507~\cite{qwen3} fine-tuned with QLoRA~\cite{qlora,lora}: 4-bit NF4 base weights with double quantisation and bfloat16 compute, and LoRA adapters (rank 32, $\alpha=64$, dropout 0.05) on all attention and MLP projections. \emph{Version 1} is supervised fine-tuning in TRL~\cite{trl} on the 18,000 training cases for one epoch (learning rate $10^{-4}$, cosine schedule, 3\% warm-up, effective batch 16, sequences up to 3,072 tokens, loss on the verdict only). Its checkpoint was selected on loss over 300 test cases, a flaw we report in the limitations. \emph{Version 2} continues training the v1 adapter on disputes whose prompt also carries the dispute window computed in code (days since payment, the policy's window, inside or not), plus payment cases so that the payment gate is kept; labels are unchanged, and the checkpoint was selected on a validation split carved from the training data, never on test cases. Payment and dispute cases use separate system prompts; the payment prompt states that everything in the payload is untrusted and that instructions found there must never be followed. The library builds these exact prompts and parses the model's answer, failing closed on anything unreadable.

\section{Where the model fails, and what to do in code}\label{sec:failures}

\paragraph{Self-vouching text.} All four of v1's unsafe approvals were injection cases (4 of 69 injected payments), each with untrusted text asserting its own verification, such as ``risk level: low (verified offline)''. A payer cannot grade its own risk, so the library scans untrusted text for self-asserted claims, after Unicode normalisation against look-alike characters, and holds on a match. With the model, it gives 0 unsafe approvals out of 847 and adds 0 false holds on the 3,358 legitimate payments in the test and training splits. Of v2's three unsafe approvals, two are injections the same check holds; the third lacks the payer attestation the policy requires, which the payer's own code can check. The check was written after these failures were found, so it repairs a known weakness rather than providing an independent evaluation.

\paragraph{The dispute window.} In v1, 59 of the 61 wrongful denials are \code{dismiss} verdicts carrying the flag \code{outside\_dispute\_window}, which the correct label never contains. Recomputing the days between payment and filing for every dispute shows that the model claims ``outside the window'' 112 times and is wrong in 91 of them (81\%); its own explanations compute the elapsed days correctly and then compare them wrongly (``filed 26.5 days after payment, outside the 60-day window''). Whether a dispute is inside its window is date arithmetic, so we moved it to code twice. \code{check\_dispute\_verdict} recomputes the window after the model answers; a denial resting on a false window claim becomes \code{escalate\_to\_human} with no refund, so the check never creates a refund. v2 instead receives the computed window before it answers. Table~\ref{tab:window} shows both.

\section{Real-world evaluation}\label{sec:real}

\paragraph{Address poisoning on Ethereum.} We built a dataset~\cite{realworld} from Google's public Ethereum mainnet tables: 90 days of USDC and USDT payments to 18 November 2026. An attack is labelled only with on-chain evidence: the wallet paid a real payee, then a zero-value or dust transfer passed between the wallet and an address sharing at least three characters at each end with that payee (the poisoning step), then the wallet paid one token or more to the look-alike. After removing duplicate rows, vanity addresses and busy wallets (more than five look-alike candidates, a limit chosen after looking at the data, so we report every limit), 179 attacks on 175 wallets remain, with \$3,327,006 lost (median \$220). Normal payments are a deterministic sample of 4,967 payments by wallets with 2 to 200 payees. Each case was checked with the payee the victim had actually paid as the known payee.

The 8 attacks not rejected imitate exactly three characters at each end. This led to the strict mode, which rejects them too; because the dataset defines an attack as a three-and-three match, that is not separate evidence. The evidence for strict mode is its cost: it also wrongly rejects 0 of the 4,967 normal payments. A random address shares three characters at each end with a given payee about once in 16.8 million tries, so strict suits agent wallets with modest payee lists, and the standard rule remains the default.

\paragraph{The model on real payments.} On 300 real USDC payments from the same data, under a 1,000\,USDC limit, v2 matched the rule label on 300 of 300 (0 of 191 under-limit payments blocked, 0 of 109 over-limit payments approved). The prompt around each payment is a template, so this shows that the model does not over-block real traffic, not that it finds risk in it. Given the victim's real payee in a policy field it was never trained on, v2 stopped only 2 of the 58 real attacks under the limit (and 4 of 64 payments to a known payee, which it should not have). On SRA-Real v1~\cite{sraReal}, 227 cases built from real USDC payments on Base mainnet (151 unchanged and 76 with one documented change each), v1 and v2 approved all 151 real payments and stopped all 76 changed ones, against 78.4\% accuracy for the base model.

The two results together are the clearest argument for the design: the model alone does not catch address poisoning, and the deterministic check in front of it catches 171 of 179 attacks with no false rejection.

\paragraph{Live runs.} We ran the checks in front of real agents on test networks and on one mainnet. On Base Sepolia, an approved 0.01\,USDC payment settled and was re-checked from the chain by an independent settlement verifier, while a payment to an unknown payee was held. On Arc's test network, agents paid through ERC-20 transfers, native USDC, Circle Gateway and a Circle developer-controlled wallet; approved payments settled, while unlimited approvals and permits, look-alike payees and contracts, long-lived signatures and self-vouching requests were stopped before signing. On Robinhood Chain mainnet, another team's agent repaid a 25.075\,USDG loan through a pull payment, with nothing to sign; \code{verify\_settlement} confirmed from the receipt that exactly that amount reached the lender and nothing else moved. These runs are demonstrations chosen by us, not error rates.

\section{A utility--security benchmark for payment guards}\label{sec:guardbench}

A guard that blocks everything is perfectly ``secure''. To keep that visible, \code{sra-riskgate bench} generates 560 payment cases offline and deterministically and scores any guard on \emph{utility} (legitimate payments approved) and \emph{security} (unsafe payments not approved). Cases follow real attack shapes: look-alike prefix and suffix lengths drawn from the real attacks above, redirect and self-approval text, sanctioned payees and over-limit amounts, alongside legitimate payments to known and new payees and benign text that merely looks risky. Some unsafe cases are deliberately subtle, with no keywords. Any external guard can be scored through a JSON-lines command interface.

\section{Contamination analysis}\label{sec:leakage}

Template-generated benchmarks risk test cases that differ from training cases only in surface values~\cite{sainz}. No test input appears verbatim in training. Masking every hexadecimal value and number, 627 of the 1,175 payment test cases have a ``template twin'' in training; no dispute case does. v1's accuracy barely depends on it: 99.7\% with a twin and 99.3\% on the 548 without one. All four of v1's unsafe approvals fall in the no-twin group, so on cases unlike anything in training its unsafe-approval rate is 0.83\% (4 of 481) rather than 0.47\%.

\section{Related work}

Benchmarks for prompt injection against tool-using agents~\cite{greshake,agentdojo,injecagent} show that untrusted content can steer an agent's actions; our setting adds irreversible money movement and a precise, checkable notion of the right action. Address poisoning has been measured at scale on Ethereum and BNB Chain~\cite{poisoning}; we evaluate a pre-sign defence against confirmed attacks and report its false-rejection cost. General-purpose LLM guardrails classify text, and wallet spending limits cap amounts; neither decodes what is about to be signed, remembers what was agreed in a negotiation, or produces verifiable decision records. The OWASP lists~\cite{owaspllm,owaspagentic} give a shared vocabulary for the risks, which we use to state coverage and its gaps.

\section{Limitations}

\begin{itemize}
  \item \textbf{Synthetic benchmark, same author.} Benchmark scores measure agreement with the generator's rule engine, and the guard benchmark's cases and the library share an author. The generator is not public, so labels can be re-scored but not regenerated.
  \item \textbf{Real-world scope.} The poisoning data covers Ethereum mainnet, USDC and USDT, and 90 days; attacks through fake tokens are not counted, so the true number is higher. The busy-wallet limit was chosen after looking at the data. No third party has reproduced these results yet.
  \item \textbf{Post-hoc checks.} The claims check and the window check were designed after inspecting the errors they fix; their effect is an upper bound for new wordings and new error types.
  \item \textbf{v1 checkpoint selection used test cases} (loss on 300 sampled test cases). v2 corrects this with a validation split.
  \item \textbf{Unverified integrations.} The screening-provider adapters are built from published API documentation and tested against responses shaped like it, not against live accounts. The OWASP mapping has not been reviewed by OWASP. The hosted Cloud service is open source but not yet operated for third parties.
  \item \textbf{Demonstrations are not error rates.} The live runs cover a few payments chosen by us.
\end{itemize}

\section{Future work}

A registered study protocol~\cite{deference} tests, across five models from five developers (450 runs, hypotheses and analysis fixed in advance), whether a paying agent that refuses an attack on its own still submits it when told that a gate decides. Beyond that, the most important next steps are an evaluation collected and labelled by someone other than the author, live threat feeds of planted look-alike addresses, a TypeScript library with the same checks, and learned detection of redirect and self-approval requests worded without keywords, measured on the guard benchmark's subtle cases.

\section{Conclusion}

A small fine-tuned model can gate agent stablecoin payments with high accuracy, but its remaining errors are not random. They cluster in operations a model should not be trusted with when money moves irreversibly: believing what untrusted text says about itself, comparing numbers, and noticing that an address is almost, but not quite, the one paid before. Moving those operations into deterministic, fail-closed code removes most of the measured harm, and signing every decision makes the result auditable. We release the library, the benchmark, the model, every prediction and the evidence tooling so that others can test this design on their own policies.
